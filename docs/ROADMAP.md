# نقشه راه دیوان

هدف: حرکت دیوان به سمت نرم‌افزارهای حسابداری ایرانی در سطح هلو، پارسیان، سپیدار و تدبیر.

> تخمین زمان‌ها برای یک نفر و حدسی است. برای فرمت‌های قانونی (مودیان، اظهارنامه، دفاتر) قبل از شروع، مستندات رسمی روز سازمان امور مالیاتی باید بررسی شود.

## اصول

1. **اول اعتماد، بعد امکانات.** هر ماژول جدید فقط روی پایه‌ای ساخته می‌شود که تست دارد.
2. **انطباق قانونی قبل از ماژول‌های تخصصی.** مودیان الزام است، نه امکان اضافه.
3. **همه‌چیز ماژولار.** هر فاز یک ماژول قابل‌فعال‌سازی است (سیستم ماژول‌ها در نسخه‌ی beta.96 اضافه شد).
4. **بدون رگرسیون.** ماژول جدید نباید رفتار ماژول‌های فعلی را تغییر دهد.
5. **قفل ماژول‌ها فعلاً «نرم» است.** برای کنترل واقعی فروش ماژول‌ها به اعتبارسنجی سمت سرور نیاز داریم (فاز ۶).

## وضعیت فعلی (انجام‌شده)

- فاکتور فروش/خرید/پیش‌فاکتور، برگشت از فروش، مرجوعی به تامین‌کننده
- پرداخت‌ها، چک و یادآوری چک، صندوق و بانک
- سند حسابداری خودکار (با اعتبارسنجی تراز)، بستن سال مالی
- گزارش‌ها: سود و زیان، ترازنامه، تراز آزمایشی ۴ ستونی، دفتر معین، پنل مالی
- پیوست فاکتور، ایمیل/اشتراک فاکتور به‌صورت PDF، محبوب‌ها، موارد اخیر
- انبارها، نقل‌وانتقال، انبارگردانی (لایه‌ی چندانباره، مستقل از `Product.stock`)
- امنیت: قفل PIN/رمز/الگو/بیومتریک، بکاپ رمزنگاری‌شده AES-256، RBAC
- سرور Express + PostgreSQL، همگام‌سازی، نصاب ویندوز/لینوکس
- بازطراحی هویت بصری (فیروزه‌ای/زعفرانی/سفالی) و fallback رنگ برای مرورگرهای قدیمی
- سیستم ماژول‌ها با کد فعال‌سازی

## فاز ۰ — پایه‌ی اعتماد (۱ تا ۲ هفته)

هدف: جلوگیری از خطای مالی و آماده‌شدن برای عرضه.

- [ ] تست خودکار برای: محاسبه‌ی فاکتور، سند خودکار (فروش/خرید/برگشت/مرجوعی)، مانده‌حساب مشتری و تامین‌کننده، بستن سال مالی، انتقال و انبارگردانی
- [ ] رفتار موجودی منفی: به‌جای چسبیدن ساکت به صفر (`Math.max(0, …)`)، یا مسدود کردن یا هشدار صریح (قابل‌تنظیم)
- [ ] تراکنشی کردن ثبت فاکتور: موجودی، پرداخت و سند با هم ثبت شوند یا هیچ‌کدام
- [ ] یکی‌کردن `Product.warehouseName` قدیمی با سیستم انبار جدید
- [ ] حذف تکرار منطق مانده‌حساب و رفع کدهای مرده
- [ ] کاهش حجم باندل (chunk بزرگ‌تر از ۶۰۰ کیلوبایت): code-splitting
- [ ] رفع سه هشدار امنیتی moderate ابزار build (`@capacitor/cli` ← `xcode` ← `uuid`) هنگام انتشار نسخه‌ی پایدار
- [ ] مرور فایل‌های باقی‌مانده: `import.ts`، `sync.ts`، `duplicate-detection.ts`، `use-form-draft.ts`

**معیار پایان:** تست‌ها در CI اجرا شوند و شکست تست جلوی release را بگیرد.

**نقطه‌ی عرضه:** بعد از فاز ۰، انتشار روی کافه‌بازار (APK از نظر فنی آماده است).

## وابستگی‌ها

- تولید ← میانگین موزون ← کاردکس
- اظهارنامه و دفاتر قانونی ← کدینگ سه‌سطحی (فاز ۱)
- فروش واقعی ماژول‌ها ← لایسنس سمت سرور (فاز ۶)
- هر ماژول تخصصی ← تست‌های فاز ۰

## قواعد کاری (از تجربه‌ی پروژه)

- ترتیب انتشار: `bump.sh` ← typecheck ← build ← commit ← push ← tag (و push تگ)
- فایل `package.json` را در پچ‌ها نفرستیم؛ وابستگی را با `npm install` روی خود ریپو اضافه کنیم
- بعد از هر پچ، یک تست دستی روی خود اپ (نه فقط typecheck)
- خروجی دستورها کوتاه باشد (`| tail`)
